## 2. 三大模块职责

### 2.1 数据处理模块
| 能力 | 实现位置 | 关键接口 |
| --- | --- | --- |
| 数据源配置 | `pipeline/sources.py` | `GET/POST /api/sources`、`POST /api/sources/{id}/probe` |
| 数据导入（编码探测 + 分块读取） | `pipeline/ingest.py` | `POST /api/pipeline/run` |
| 数据清洗（缺失/异常/重复/类型） | `pipeline/clean.py` | 同上（由 `params` 控制） |
| 特征构造 | `pipeline/features.py` | 同上 |
| 数据划分 | `pipeline/split.py` | 同上（`split_protocol`） |
| 存储与批处理汇总 | `pipeline/store.py` | `GET /api/analytics/*` |
| 数据版本记录 | `pipeline/versioning.py` | `GET /api/versions`、`/activate`、`/quality` |
| 独立导入/更新工具 | `tools/etl.py` | 命令行 |
| UI 截图工具（开发辅助） | `tools/ui_shot.py` | 命令行（CDP 驱动无头浏览器） |

### 2.2 核心算法模块

## 3. 可复用的数据处理流程与数据版本

### 3.1 流水线六阶段
```
① ingest     编码探测 → 列名规范化 → 分块读取 → 类型强制 → 原始画像
② clean      记录过滤 → 取值规范化 → 缺失值处理 → 异常值处理
③ features   楼层解析 / 户型 / 楼龄 / 时间 / 位置 / 小区热度 / 类别编码 / 防泄漏校验
④ split      时间切分（默认）或随机切分，产出 train / valid / test
⑤ store      SQLite 明细表（replace 或 upsert）+ Parquet 列存快照 + 划分集文件
⑥ aggregate  11 类预聚合指标 → SQLite agg_* 表 + JSON 快照
```

### 3.2 数据版本记录结构
每个版本 = 一个 JSON 文件（`data/registry/<version_id>.json`）+ 一条索引项。记录内容：

```jsonc
{
  "version_id": "ds-20261011-224500-a1b2",
  "created_at": "2026-10-11 22:45:00",
  "source_id": "lianjia_bj_raw",
  "source_license": "CC0-1.0 (Public Domain)",
  "raw_checksum": "<原始文件 SHA-256>",
  "params": { "missing_strategy": "median", "outlier_strategy": "iqr", "split_protocol": "time", ... },
  "stages": [ { "stage": "ingest", "rows_in": 318851, "rows_out": 318851, "seconds": 12.4, ... }, ... ],
  "clean_report": { "filter": {...}, "missing": {...}, "outlier": {...} },
  "feature_report": { "model_features": [...], "forbidden_check": "passed" },
  "split_meta": { "protocol": "time", "train_rows": ..., "test_rows": ..., "train_period": [...], "test_period": [...] },
  "target_stats": { "mean": ..., "median": ..., "std": ... },
  "fingerprint": { "rows": ..., "columns": {...列级分位数...} },
  "checksum": "<产出 Parquet 的 SHA-256>",
  "status": "success",
  "active": true
}
```

**用途**：
1. **可复现**：给定 `version_id` + `params`，可完整重放数据；
2. **可对比**：`GET /api/analytics/compare?a=&b=` 对比两版本的规模、清洗损失、目标分布；
3. **可追溯**：任何模型记录都带 `version_id`，能回答「这个模型是用哪份数据、哪套参数训练的」；
4. **失败留痕**：流水线抛错时也会写入 `status="failed"` 的版本记录（含 traceback），作为失败案例。

### 3.3 批处理与增量更新
- **分块扫描**：CSV 以 `chunk_size`（默认 20 万行）迭代读取，内存占用与文件大小解耦；
- **切分工具**：`tools/etl.py split` 可把大文件切成 `part-0000.csv …`，便于分批/并行处理；
- **增量更新**：`tools/etl.py update --source X --csv new_batch.csv` 走同一套清洗与特征流程后，
  以 `house_id` 为主键做 upsert 写回明细表，支持周期性追加新成交数据；
- **预聚合**：仪表盘所需指标在流水线末尾一次性算好并落表，前端查询不再全表扫描（30 万行 → 毫秒级响应）。

## 4. 算法层设计

### 4.1 统一契约
`algorithms/registry.py` 为每个算法声明：`task / interpretable / inputs / outputs / params[] / metrics / pros / cons`。
前端据此**自动渲染参数表单**，后端据此**自动校验参数**（`validate_params`），实验脚本据此**自动跑对比**。

### 4.2 价格预测
| 算法 | 可解释性 | 说明 |
| --- | --- | --- |
| `linear_ols` | 系数直接可读 | 基线，给出性能下限 |
| `ridge` | 标准化系数可读 | L2 正则，缓解共线性 |
| `hgb` | 置换重要性 + 近似局部归因 | 精度主力 |
| `rf` | Gini 重要性 | 对照 |

**可解释性实现**：
- 全局：线性模型输出系数表；树模型输出置换重要性（`permutation_importance`, neg-MAE, 5 次重复）；
- 局部：单条房源预测时输出每个特征的贡献度。线性模型贡献 = `coef × (x − x̄)`（精确）；
  树模型贡献 = `标准化偏离 × 归一化重要性 × |预测值|`（近似，前端明确标注为「方向性参考」）；
- 预测区间：基于测试集残差标准差给出 90% 区间。

### 4.3 推荐
| 算法 | 家族 | 可解释性 |
| --- | --- | --- |
| `popularity` | 基线（可解释） | 关注度 × 新鲜度 × 性价比加权，理由可读 |
| `content_tfidf` | 内容推荐 / 相似度 | TF-IDF 文本向量 + 余弦相似度，输出命中偏好 |
| `item_cf` | 协同过滤 | Item-based 余弦（含收缩系数）/ SVD 矩阵分解 |
| `hybrid` | 混合 / 召回排序 | 三路召回 + 归一化加权 + 硬约束过滤 |
| `similar_item` | 相似度计算 | 标准化特征空间近邻，**可在真实数据上评估** |

**协同过滤的工程要点**：
物品-物品余弦相似度按「求和聚合」可分解为一次稀疏矩阵乘法：
`score_j = Σ_{i∈I_u} cos(i, j) = v · Mn[:, j]`，其中 `v = Σ_{i∈I_u} Mn[:,i]`。
这使得在 30 万候选物品上对每个用户全量排序的代价降到 `O(nnz)`，无需构造 30 万 × 30 万 的相似度矩阵。

## 5. 前端设计
- 单页应用，零构建依赖（原生 ES + ECharts，ECharts 已本地化到 `backend/web/vendor/`）；
- 11 个功能页对应三大模块；长任务（流水线 / 训练 / 离线评估）走后端任务队列 + 前端轮询；
- 价格配色遵循中国市场惯例：**涨/高 → 红，跌/低 → 绿**；
- 所有图表使用浅色主题，正文与数据分别使用无衬线与等宽字体。
